# Database and access design

`supabase/migrations/20261031080538_initial_tarozi.sql` is the authoritative schema. The migration filename was generated by Supabase CLI, not invented manually.

## Data relationships

```text
auth.users -> profiles
auth.users -> seller_memberships -> sellers -> branches -> offers
categories -> products -> variants -----------------------^ 
offers -> immutable price_observations
auth.users -> shopping_lists -> shopping_list_items -> products / variants
auth.users -> favorites -> products
auth.users -> alerts -> products
alerts + price_observations -> notifications
auth.users -> price_reports -> offers
auth.users -> search_events -> products
private.admin_users controls admin privileges
private.audit_events records price changes and seller moderation
```

All public tables have row-level security and explicit grants. Public catalog and price views are read-only to anonymous clients; pending/suspended sellers cannot appear in public results. Offer history uses recorded pack quantity and monotonically increasing offer versions, including multiple updates inside one transaction.

`offer_catalog` is a security-invoker view, so it preserves the base tables' access rules. Private lists, alerts, favorites and reports are scoped to the authenticated user. A caller cannot add seller memberships or rewrite price observations. Only notification `read_at` can be updated by the owner; notification contents are database-generated.

## Privileged functions

Security-definer functions are limited to the non-exposed `private` schema, have empty search paths, and have default PUBLIC execution revoked. Role/ownership predicates read protected membership records. Trigger functions only create constrained profile/membership/history/audit rows. Bounded alert and aggregate/audit readers explicitly check the current identity and required permissions.

Public RPC entry points are security-invoker functions. `save_shopping_list` and `publish_price_import` use normal RLS and execute atomically. Internal helpers are not included in the Data API's exposed schemas; do not add `private` to those schemas.

## Important limits

- Seller approval is a recorded administrator decision, not proof that every quoted price is authentic.
- Stock is seller-reported. There is no reservation or purchase-confirmation subsystem.
- The backend records source declarations and timestamps; uploaded evidence/OCR is deferred.
- Interest is deduplicated by user but is not statistically representative demand or a sales forecast.
- Split-basket estimates do not solve routing, credit terms, unknown fees or all quantity-tier/minimum-spend combinations.
- Existing frontend-local accounts are not migrated automatically.

## Validation evidence

Tests execute the actual migration, seed, functions, triggers and policies in PGlite/PostgreSQL with minimal `auth.users`/`auth.uid()` fixtures. They switch to actual `anon` and `authenticated` database roles. They test seller self-approval, cross-seller writes, immutable history, spoofed user metadata, private saved lists, transaction rollback, notification ownership, import authorization and small-group suppression.

The auth fixtures do not simulate Supabase GoTrue, email delivery, PostgREST schema exposure or a hosted deployment. Verify those against the selected Supabase project before calling the service live. No Docker runtime or hosted database was available during the local checks.
